# 实战记录与参数参考

来源：用本 skill 处理 *Mili - In Hell We Live, Lament*（Limbus Company 主题曲，MV 3:45.4，HEVC 1080p30，AAC 48k）
的一次完整实战。所有数字都是实测值，可直接当基准。

## 一、视频摸底

```
时长 225.408 s · 视频 HEVC 1920x1080 29.97fps · 音频 AAC 48kHz 立体声
字幕轨：无  → 只能走硬字幕 OCR
```

## 二、硬字幕 OCR 的实测参数

| 项 | 值 |
|---|---|
| 抽帧 | `fps=2`，字幕条带 `crop=1920:140:0:940`（底部 140px） |
| 帧数 | 451 张（原图一套 + 增强一套） |
| 时间基准 | 第 n 帧 = `(n-1)/2` 秒 —— 用 LRC 首句校准（LRC 23.721 ↔ 帧 48 → 23.50） |
| OCR 速度 | 451 帧 **10~15 秒**（Windows OCR，很快，别怕多跑） |
| 识别率 | 原图版 302 帧 / 增强版 274 帧 → 合并去重后 317 帧有字 |
| 合并结果 | 101 个字幕段（含碎片） |

**增强滤镜（对白字非常有效）**：
```
-vf "format=gray,eq=contrast=2.4:brightness=0.12,scale=iw*2:ih*2:flags=lanczos"
```

**红字/渐隐字**：两套图仍然会碎（`Buc!l p op e Vet`），
认命 —— 用"多帧冗余 + 模糊匹配"拼，或者直接用网上的 LRC 文本校正。

## 三、LRC 获取与校验

三处歌词站内容**完全一致**（69 行、毫秒级）：`lrc6.com` / `wagequ.com` / `lrc.64h.cn`。
说明这类热门曲目直接搜 "<歌名> lrc" 即可，不必自己从零做。

**锚点法校验（align-lrc.py）**的实测输出：
```
LRC 69 行 · 高置信锚点 32 个 · |Δt| 中位数 0.28 s · 最大 3.52 s → PASS
```

**判据**（重要）：
- 用**高置信锚点法**，不要用"顺序对齐 + 低阈值" —— 后者一个假匹配会让后面全错（实测从 52% 掉到 20%）。
- **中位 |Δt| < 0.6s** ⇒ 版本一致；匹配率低通常是 OCR 碎的，不代表版本不同。

## 四、起音与 MIDI

实测（`onsets-midi.py`，2.4 秒跑完 225 秒音频）：

```
起音 1612 个（7.2 个/秒）· 音高 p5/p50/p95 = 38 / 56 / 78
```

**分频段阈值**（这首摇滚/金属曲的实测最优值）：
- 低频 0–200 Hz（底鼓/贝斯）：`thr=1.1, dist=0.06s`
- 中频 200–2500 Hz（人声/吉他）：`thr=1.1, dist=0.06s`
- 高频 2500–14000 Hz（镲）：`thr=1.3, dist=0.05s`
- 合并去重窗口：55 ms 内取最强

**密度判据**：3–12 个/秒 正常。这首 7.2 个/秒 ✓

## 五、已知不可靠环节（如实告知使用者）

1. **音高是估计值**：FFT 谱峰，遇到鼓和和声会偏。做视觉可以，当乐谱不行。
2. **网上 MIDI 站**（midishow 等）经常整个不可达，别指望。
3. **伴奏分离**（Demucs 等）能显著改善音高，但需要额外模型与算力 —— 本 skill 不含。

## 六、路径与编码（Windows 专属坑，吃过大亏）

- Git Bash 的 `/tmp` ≠ Windows Python 的 `/tmp`：跨工具传路径一律 `cygpath -w`。
- Python 往管道/控制台打印中文，控制台是 GBK 时会 `UnicodeEncodeError`：
  脚本开头统一 `sys.stdout.reconfigure(encoding='utf-8', errors='replace')`。
- Python 原始字符串**不能以反斜杠结尾**（`r'...\scripts\'` 会语法错误）—— 拼路径用 `/`。
